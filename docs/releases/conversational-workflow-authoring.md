# Conversational workflow authoring — first increment

Based on `codex/render-supabase-migration`; integrated through `450d84cee4f38b9fd7443d6fe10168f644df4901` in the isolated feature checkout.

## Reviewable behavior

The workflow library and saved workflow editor offer **Build with chat**. Each message makes one metered text-model turn and returns typed changes. Follow-up messages refine the current unapplied proposal. The user inspects a static step/form preview and exact JSON changes, then explicitly applies the proposal to a draft. Unsaved editor changes disable chat entry. Apply errors leave local state intact. Published Apps, execution, schedules and posting retain their existing separate interfaces and authorization paths.

`server/lib/workflowAuthoring.ts` is the shared domain service. The tRPC router and MCP adapter call it directly. There is no second execution engine, arbitrary code generation or generic remote execution facility. The existing `appVersionId` representation of both `app` and `run_workflow` is unchanged. Graphs, form fields and models use the existing shared schemas and validation helpers. Pinned Apps use the existing resolver.

Every action rechecks active organization membership and workflow roles, under a membership lock. Draft and App reads are tenant-scoped. Static inspection checks referenced account/media/product ownership using local IDs only. It never decrypts credentials or reads/uploads image bytes. Nested definitions are bounded before expansion and still pass the existing resolver's limits. Runtime connection status, media approval, model availability, billing and provider-specific constraints remain execution-time checks.

Proposals are immutable `authoring.proposed` activity events containing the base hash, target revision, typed changes, proposed snapshot and preview. Applying requires the reviewed proposal hash and original revision. The transaction uses the existing organization lock, conditional revision update and audit hash chain. `authoring.applied` events hold durable request receipts; replays return the original ID/revision. Another user's proposal cannot be read or applied. A replay does not claim that the current draft still matches the original receipt.

Chat first commits an `authoring.requested` reservation, then uses `aiScope`, `listLLMModels`, `requireLatestGptTextModel` and `invokeLLM`. The new operation has a conservative metering estimate. Provider network retries remain those of the existing LLM infrastructure; the authoring agent itself makes one logical model call and has no tools or repair loop. Model output is parsed and validated before storing a proposal. No new provider route or credential is introduced.

## Limits and deliberate omissions

- 80 typed edits per proposal; existing 40-node / 100-edge draft schema; four nested App levels. Static preflight inspects at most 160 definition nodes (including repeated calls), which can be stricter than the existing 160 expanded-step / 400-edge execution limits.
- 6,000 characters per chat message, twelve history messages, 96,000 characters of draft/App/history context, and 8,000 output tokens. Discovery and chat share a scoped App contract catalog: at most 100 recent versions and 32,000 characters of complete contracts, with an explicit truncation flag. Contracts contain exact callable input IDs, declared types, form constraints and output IDs/types, using the existing App reader and normalization. Archived Apps are excluded. Multi-input composition uses those IDs with the existing `inputMapping` mechanism; large omitted contracts require explicit discovery/readApp outside the one-turn in-app agent. Text context is data, not an authority to execute tools.
- Static preview is a step/form/configuration summary, not a generated-media preview, quote or proof a workflow can run. Empty/incomplete drafts can carry readiness warnings; malformed graph/form/model definitions fail validation.
- Up to 32 explicit refinement turns may build on an unapplied proposal. Each request binds the parent ID/hash and original saved revision. Replacement is atomic with proposal storage; old proposals cannot apply or branch again. The latest snapshot retains all prior proposed changes, but its apply still checks the original draft revision/hash. A failed refinement preserves the previous preview and uses the same explicit recovery controls. Chat history is browser-local; proposals and apply receipts are audited server-side. There is no autonomous model/tool loop.
- Failed or interrupted chat request IDs remain reserved. The UI checks the exact original request's status before retrying. Lost successful responses recover the stored proposal; unreceived requests reuse the original payload/key. Recorded failures offer an explicit **Start new metered attempt** action. Pending/uncertain requests require a fresh status check and explicit **Abandon unresolved attempt** before another attempt; abandonment fences late proposal persistence under the organization lock. It cannot cancel/refund a provider call already in progress, and another attempt may incur another charge. No unknown status silently starts new work. There is no automatic recovery worker.
- Pre-reservation rejections (such as stale revision or oversized context) offer **Reset chat for corrected request**. Reset atomically closes an unreserved request ID so a delayed transport cannot reserve it later, and clears chat history to release context space. For an existing, clean editor, this explicit action reloads the latest saved draft and revision without remounting; unsaved edits disable reset. If the old request became pending or completed, reset returns that outcome instead of silently starting over. Oversized draft content still needs correction before resubmitting; there is no automatic rebase over unsaved edits. A lost reset response must be checked again before reset completes.
- Existing Optimization Studio plans are preserved, but editing their plan structure is outside the typed operation set. Publishing, enabling automation, executing, spending generation credits and external posting are not MCP capabilities.
- Activity storage is reused for proposals. Migration `0021_authoring_oauth` adds two private, RLS-enabled authorization tables; existing workflow/version schemas and execution semantics are unchanged. Proposal retention follows the current activity-log retention policy. Large-scale proposal search, pagination and a dedicated revision browser are follow-up work.

## MCP connection implementation

The production server registers a bounded HTTP mount before general parsing/site routing. It returns **503 while `AUTHORING_MCP_ENABLED` is absent or false**. Enabling it also requires a valid HTTPS `APP_ORIGIN`, `AUTHORING_MCP_CLIENT_ID` and an exact JSON redirect allowlist in `AUTHORING_MCP_REDIRECT_URIS`. Incomplete/unsafe enabled configuration fails startup. No production settings or grants were created during implementation.

The official `@modelcontextprotocol/server` 2.4.0 SDK serves Streamable HTTP at `/mcp/authoring`. Eight tools cover connection/workspace context, block discovery, draft/App reads, typed proposals/refinement, static preview, proposal status and draft-review requests. The host composes typed changes; MCP cannot call the app's model endpoint. The in-app chat retains the existing metering infrastructure.

A narrow authorization-code server shares the existing server-verified EvokeLoop browser sign-in. It supports one pre-registered **public** client, PKCE S256, exact client/redirect/resource binding and issuer identification. No DCR, arbitrary metadata fetching, refresh token, new signing secret, password handling or upstream token forwarding is introduced. `/mcp/oauth/authorize` renders a same-origin, explicit consent form listing only workspaces where the user can author workflows. Consent selects one workspace and the requested read/draft scopes. Denial returns `access_denied`, state and issuer to the validated callback. Handshake nonces/codes expire after five minutes. Authorization-code exchange is atomic and single-use. Only hashes of high-entropy nonces, codes and tokens are stored.

Access grants last **30 minutes**, then require authorization again. `/mcp/connections` lists the latest 100 grants and lets the signed-in owner revoke them. Browser sign-out does not itself revoke an OAuth grant. Each domain operation locks/rechecks the connection and current membership inside its transaction. A token cannot access another workspace even when the user belongs to both. Grant issuance, consent, revocation and draft changes are audited without token values. Expired handshakes older than one day are cleaned up for the user when starting another handshake; grant/audit retention is otherwise unchanged.

The mount enforces the configured host, HTTPS in production, same-origin browser writes, bounded bodies (8 KiB forms / 256 KiB MCP), no-store responses and per-process IP limits (60 requests/minute; 30 authorization/token attempts per 15 minutes). Review/consent pages escape all workspace/proposal text, forbid framing and scripts, and use restrictive CSP. Multi-instance global throttling remains deployment infrastructure work.

**MCP cannot directly apply a draft.** `apply_reviewed_workflow_draft` checks scope and proposal identity and returns an EvokeLoop review URL. The connected account must sign in, inspect the complete snapshot, and deliberately POST the apply form on EvokeLoop. Grant ownership, scope, expiry/revocation, active membership, proposal identity and original draft revision are checked again. The request ID makes lost apply responses safe to retry. `read_workflow_proposal_status` reports awaiting-review, replaced or applied (including draft ID/revision). A reviewed hash binds identity; the authenticated review POST supplies the application-side approval boundary. ChatGPT per-action prompts should also be configured; they are not trusted as the sole approval mechanism.

### Authorized release and connection checklist

1. Parent coordinates review, merge and deployment of this PR, including `0021_authoring_oauth`. Leave MCP disabled initially; in-app refinement can ship independently. No workflow schema migration is needed.
2. At action time, obtain explicit approval to expose the MCP endpoint and configure the public OAuth client. In ChatGPT's MCP management UI, use a pre-registered public client (token authentication `none`) and copy its **exact displayed redirect URI**. Set the chosen public client ID and JSON redirect allowlist; do not invent or wildcard callback URLs. No client secret is needed by this implementation. If the account UI cannot configure this supported mode, stop and resolve that compatibility before enabling access.
3. After approved configuration, set `AUTHORING_MCP_ENABLED=true` on the app host. Verify TLS/proxy behavior, unauthenticated discovery/challenge, no-store headers and body/rate limits. The authorization metadata is `/.well-known/oauth-authorization-server`; protected-resource metadata is `/.well-known/oauth-protected-resource/mcp/authoring`.
4. With specific connection approval, sign in and authorize one test workspace. Start with `workflows:read`, then explicitly authorize `workflows:draft` for proposal work. Do not turn on persistent automatic write approval. Verify the real client's PKCE/resource/client handling and callback/issuer checks.
5. Exercise discovery, App contracts, multiple refinements, static preview, app-side human review/apply, status recovery, concurrent edits, expiry, cross-workspace denial and revocation. This can use deterministic typed proposals and does not require paid generation or external workflow execution.
6. Report actual end-to-end results before calling the connector usable. Local HTTP tests cannot establish a user's ChatGPT account/UI availability or production proxy behavior. No connection has been installed or verified in production yet.

## Verification

The scoped Vitest suite uses PGlite with repository migrations, mocked model responses, real RSA JWT signing/verification with local test keys, and component tests. It covers tenant and membership checks, duplicate proposals/applies, concurrent revision conflicts, reviewed hashes, invalid graphs/forms/models, nested recursion/depth/breadth, pinned App compatibility, missing references, static-preview network isolation, model metering context, untrusted prompt content, invalid model output, HTTP auth boundaries, SDK tool dispatch, scope checks and review/apply UI behavior. Existing workflow execution tests use their provider mocks.

Initial scoped validation passed 72 tests, TypeScript and client/server/worker/MCP builds, but full CI subsequently found the reserved tRPC route name `apply`. The public procedure is now `applyDraft`; a real, unmocked root-router import test guards startup. Additional regressions cover status recovery, explicit abandonment, late-result fencing, unchanged-message new attempts, bounded multi-input App contracts and exactly advertised MCP scope grants. A local full-suite run reached 1,496 passing tests; seven files could not complete because the local isolated integration database was unavailable. Use the corrected commit's GitHub CI, which provisions PostgreSQL, for the full result. On Windows, build components are invoked directly rather than the package script's Unix `cp` command. Vite emits a large-chunk advisory.

No live model call, paid generation, external workflow execution, production endpoint configuration, production OAuth grant, ChatGPT connector installation, deployment or release-branch merge was performed. Local isolated tests create synthetic authorization codes/grants only. Authenticated ChatGPT testing remains a later authorized verification step. Local HTTP tests exercise metadata, consent, code exchange, MCP tool calls and the authenticated review/apply form against an isolated database and mock sign-in.

The current increment adds regression coverage for parent proposal identity, cumulative refinement, stale saved revisions, superseded applies, exact retry/metering, OAuth PKCE/client/callback/resource binding, authorization denial, concurrent code redemption, hashed token storage, grant-scoped tenants, revoked memberships/grants, CSRF, body/host boundaries, human review/apply and lost-response receipts.
